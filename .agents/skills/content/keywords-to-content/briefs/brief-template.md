## Worked Example Only

This is an example of a filled brief. It is here to show what “complete enough to execute” looks like.

- Primary keyword: `LLM evaluation`
- Supporting keywords:
  - `LLM eval metrics`
  - `RAG evaluation`
  - `LLM-as-a-judge`
  - `hallucination detection`
- Search intent: ML engineer wants to understand how to evaluate LLM application quality in practice
- Intent type: Practitioner / technical educational
- Target reader: ML engineer or platform engineer building or operating LLM applications
- Funnel stage: Mid-funnel
- Asset type: Technical blog post
- Primary CTA: Try Phoenix or review the open-source eval workflow
- Core angle: Traditional ML evaluation is not enough for LLM apps; practitioners need a framework for evaluating relevance, hallucinations, retrieval quality, latency, and cost in production systems
- Required sections:
  - What is LLM evaluation?
  - Why traditional ML eval is insufficient
  - Core eval dimensions: relevance, hallucination, toxicity, retrieval quality, latency, cost
  - Human eval vs automated eval
  - LLM-as-judge
  - RAG evaluation example
  - Code walkthrough
  - Common failure patterns
  - How Arize / Phoenix fits
  - FAQ
- Existing Arize pages to reference:
  - Phoenix docs
  - LLM observability pages
  - RAG evaluation pages
  - tracing or OpenInference pages
- Assets required:
  - product screenshot
  - code example
  - possible benchmark or comparison table
- SME input required:
  - engineer quote or practitioner guidance
  - validation that the eval workflow reflects current product reality
- Cannibalization concerns:
  - check for overlap with existing Arize posts on RAG eval, hallucination detection, or Phoenix comparisons
- Notes:
  - this page should answer the core question quickly
  - examples should come before abstract theory
  - avoid generic AI-SEO intro copy
